本文件交给报告撰写组员使用。它说明各章讲什么、配什么图、到哪里找资料；正式报告仍由撰写者组织语言和排版。

项目题目：**厦门本岛工作日早高峰共享单车的源汇区域与区域间流动模式挖掘**。

## 1. 引言

### 内容重点

- 从早高峰出行切入：共享单车能连接居住区、园区与公共交通节点，定位点中包含出发、到达和经过关系。
- 提出项目的问题：哪些区域是源或汇，区域之间怎样往来，哪些通道和区域序列反复出现？
- 简述解决思路：Spark处理大规模数据，挖掘流动区域与模式，MobilityDB管理时空结果，FastAPI与地图界面支持探索。
- 交代研究范围为2020年12月21日至25日、每日06:00–10:00、厦门本岛。后续章节以图注和筛选标签承接这个范围。

建议篇幅半页至一页。开头用具体的城市出行问题，不必长篇介绍“大数据时代”。如需现实背景数字，可引用2020年厦门已运营2条地铁、71.9公里的资料，来源见[城市背景资料卡](interaction-results-storyline.md#10-城市背景资料卡)。

资料入口：[项目计划“一、项目定位与边界”](../project-plan.md)、原始数据论文、第9章资料卡。

## 2. 数据来源与介绍

### 内容重点

数据来自Cai等人的数据描述论文 [Comprehensive spatiotemporal dataset of shared bicycle operations in Xiamen China](https://www.nature.com/articles/s41597-025-06534-z)。正文介绍来源、时间范围、空间范围和字段，读者应能理解输入数据为什么同时支持起终点与路径分析。论文页面不便读取时可使用[作者稿PDF](https://www.nature.com/articles/s41597-025-06534-z_reference.pdf)。

规模建议用一张简表：

| 数据 | 规模 | 在项目中的用途 |
|---|---:|---|
| 原始GPS轨迹点 | 2,849,243点 | 轨迹恢复、地图匹配、通道流与区域序列 |
| 开关锁事件 | 441,350行，配成220,675条行程 | 起终点、源汇与出行流 |
| 匹配后有效数据 | 76,958条有效轨迹，2,119,826点 | 下游挖掘和MobilityDB轨迹发布 |
| 天气数据 | 小时级 | 标识晴天集与12月23日雨天 |
| OSM道路与功能要素 | 福建PBF快照、本岛边界 | 自行车路网、地图匹配和区域功能背景 |

强调课程要求至少10万轨迹点，而本项目原始点数约为其 **28.49倍**；完成筛选和匹配后仍超过200万点。原始点数和有效点数各写清楚。

论文还提供电子围栏数据，介绍原数据组成时可提及；本项目实际分析主线使用GPS、开关锁、天气与OSM。GPS与订单通过区域级结果联系，各自承担路径和行程起终点两个视角。

### 建议图表与资料入口

- 一张数据规模表；一张字段示例表，选车辆编号、经纬度、时间、锁状态和稳定行号 `source_row`。
- 可配本岛研究范围图，复用第9章总览的底图范围，不提前展开结果。
- 实际文件和哈希：[config/data-contract.lock.json](../../config/data-contract.lock.json)。原始规模与冻结观测：[config/baselines.json](../../config/baselines.json)。
- 输入读取与转换：[datasets.py](../../src/find_bike_routes/datasets.py)、[convert_raw_excel_to_csv.py](../../scripts/convert_raw_excel_to_csv.py)。探索记录在 `notebooks/`。
- 路网快照名称与时间按数据契约填写；它是辅助地理数据的版本，与2020年的骑行采样时间分别列出。

## 6. 数据管理层设计：MobilityDB

### 内容重点

围绕“如何保存会随时间移动的骑行路径，并让前端查询一个时间内经过某处的轨迹”来写。

1. 说明为什么同时使用PostGIS与MobilityDB：区域用空间几何，骑行路径用带时间的 `tgeompoint`。
2. 介绍主要数据关系：片区包含区域，区域对应时段画像，流表连接起终区域，轨迹表支持联机时空查询。配一张简化ER图。
3. 介绍轨迹如何入库：按完整匹配道路构造时序路径，每个已知路径片段形成sequence，整条轨迹保存为sequence set。配一幅有转弯和断点的小时序示意图。
4. 说明GiST索引和查询顺序：时空包围盒初筛，`atTime`限制时间，`eIntersects`判断相交，再返回唯一轨迹数及样例路径。
5. 说明发布方式：Parquet结果离线导入，同一活动版本通过事务替换，API使用只读角色。

## 7. 业务逻辑层设计：FastAPI

### 内容重点

说明API如何把挖掘结果和时空查询转为前端能够消费的数据。推荐用“点击区域 → 请求 → 数据库查询 → GeoJSON → 地图与详情更新”的调用图贯穿本章。

| 接口 | 重点解释 |
|---|---|
| `GET /api/regions` | 返回区域、片区、边界和每日每时段指标，供前端按选择聚合 |
| `GET /api/flows` | 按矩阵、日期、小时返回区域流与检验信息，晴天集提供稳定显著集合 |
| `GET /api/sequences` | 读取Parquet，按连续支持度门槛、相邻性和Top-N筛选模式 |
| `POST /api/tracks/query` | 接受区域或矩形与时间窗，返回相交轨迹总数和样例几何 |
| `GET /api/health` | 确认服务、数据库及发布数据可用 |

简述Pydantic参数校验、参数化SQL、发布摘要核对和GeoJSON输出。讲清前后端职责：接口提供单小时切片，前端按用户选择合并时段与日期；序列支持度保留其原有计数。

资料入口：[api.py](../../src/find_bike_routes/api.py)、[flows.sql](../../database/queries/flows.sql)、[tracks.sql](../../database/queries/tracks.sql)、[Web API spec](../../.scratch/web-api/spec.md)。

本章可用一小段已完成的真实HTTP验收说明交互响应能力：[2026-09-10验收记录](../../artifacts/runs/20260910-acceptance-web-api/acceptance.md)中，健康、区域、双流与序列接口均小于1秒，三组轨迹查询均小于1秒，课程预设轨迹查询门槛为5秒。这是该次本机全量发布版的实测；参数、响应字节数和完整JSON均在同目录。正文选区域接口约0.22秒、大框4小时轨迹查询约0.92秒两个例子即可。

## 8. 交互层设计

### 内容重点

本章解释界面如何组织信息和交互，第9章负责用它分析城市。按真实使用过程写：进入地图、选日期与时间、切换分析图层、选择对象、进入局部聚焦、退出恢复。

- 总体布局是一张Leaflet地图、顶部控件和按状态出现的说明/详情面板。三种分析图层共享地图。
- 源汇用以零为中心的红蓝色阶；流动用有向连接、列表和片区弦图；通勤链用按顺序连接的区域与选中态。
- 源汇和流动支持单日或连续日期范围，也有晴天集快捷恢复；通勤链使用晴天集或单日。时段、日期和跨日平均/合计的含义在界面中可见。
- 区域详情组织骑行活动、方向玫瑰和功能构成；区域点击或矩形框选都能查询样例轨迹。
- 聚焦有独立时间选择，退出时恢复进入前的分析内容与地图位置。列表、控件标签、键盘操作和非纯颜色表达让结果更容易操作和阅读。
