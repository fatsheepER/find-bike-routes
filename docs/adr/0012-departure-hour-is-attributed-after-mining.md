# 时段维不进挖掘，改为挖掘后的支持度分解

计划第 6 节的附加实验（P1）是 item = 区域 ID + 出发半小时桶，用 PrefixSpan 挖带时段的通勤链。我们取消这个做法：只挖一次不带时间的区域序列，再拿模式集回扫序列库，给每条模式加四列按轨迹起始小时分解的支持度（`support_h06`…`support_h09`），四列可加、合计等于 `support`。

理由有两条。第一，复合 item 得不到额外信息：出发时间是整条序列的常量，item = (区域, 桶) 的模式不可能跨桶，因此该做法与「按桶把序列库分开、各挖一次」在模式集合上完全等价，差别只在阈值分母。而后验分解严格更强——它给出同一条链在四个时段的完整分布，分桶挖掘只能告诉你某桶里这条链在不在阈值以上。第二，为拿到 `contiguous_support`，模式集回扫序列库本来就必须做一遍，四个计数是这遍扫描的零边际成本产物。

计划原文写的是半小时桶，改为整点时段还顺带消掉一个术语冲突：`CONTEXT.md` 的「时段」是 6–10 点的四个整点段，`region_metrics`、`flow_od`、`flow_channel` 全用 `hour`，再立一个半小时粒度会让同一份报告里出现两套时间口径，而 6:00–6:30 只有约 1,363 条序列，细粒度换不来样本。

## Consequences

- `docs/project-plan.md` 第 6 节删去 P1 一句，改为后验时段分解；第七节验收条件补「每条模式按出发时段的支持度分解」。
- 时间口径与 `CONTEXT.md` 的「时段」一致：轨迹按起始时刻归段，与画像表可直接交叉引用。
- 想回到分桶挖掘随时可以——序列库物化成 `track_sequences` 且带 `start_hour`，按桶过滤再挖一次即可。
