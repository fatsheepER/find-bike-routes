# 匹配按轨迹逐条走普通 UDF，路网以列式载荷广播，不做 bbox 空间分片

按 `TRACK_ID` 聚合成一行一条轨迹后交给一个返回嵌套 struct 的普通 Python UDF 跑 HMM/Viterbi，再 explode 展开；路网以紧凑列式载荷（边表定长字段 + 路段几何 WKB）广播，executor 端用模块级缓存重建一次 `STRtree` 与 `MultiDiGraph`。选普通 UDF 是因为计划禁用的是 pandas UDF、pandas-on-Spark 与 Spark Connect，普通 UDF 不在其列，且 ADR-0001 已经为这个模式立过先例；选列式载荷而非广播建好的匹配器对象，是因为 `MultiDiGraph` 的平行边在等长时按插入顺序被选中，把重建口径定成「按 `edge_index` 排序后插入」才使这个选择完全确定。

## Considered Options

计划为广播内存不足的情况留了一条「按 bbox 空间分片、跨片轨迹单独串行处理」的退路，**我们不实现它**。实测：单日 15,527 条轨迹匹配耗时 31.2 秒（单线程 pandas，含路由缓存），五天约 163 秒单核；广播载荷的几何不到 1 MB。分片方案要额外处理跨片轨迹、要维护片边界与两套代码路径，换来的是一个不存在的问题的解法。

## Consequences

- 每条轨迹的点要序列化进 UDF 一次；按中位 28 点算可以忽略。
- 路由缓存留在 executor 进程内，只影响速度不影响取值，因此不同分区的缓存命中差异不会造成结果的不确定性。
- 若将来数据规模涨到广播吃不下，正确的做法是回到这条决策重新评估，而不是在别处打补丁。
