# 路网抽取是独立的一个阶段，产物物化成 Parquet

计划把「路网构造」和「并行地图匹配」写成同一步，我们把它们拆成两个阶段、两个 CLI、两套运行产物，路网落 `data/processed/network/` 的 `network_segments` 与 `network_edges` 两张 Parquet，匹配阶段只读 Parquet。拆分的理由不是性能——从 41 MB PBF 抽出全岛路网只要 6 秒——而是路网决定了 12,359 条物理路段、24,718 条有向边、1,761.8 公里这些会被写进报告的数字，以及后续承载街道图层与区域标签所需的路段等级与路名；这些应当是可查询、可成图核对的产物，而不是每次重算出来的中间态。

## Consequences

- 路网抽取的 tag 规则（`highway` 排除集、`bicycle` 允许集、单向与反向自行车道的判定）按 ADR-0002 写死在代码里，并序列化进路网阶段的运行产物，因此「这版路网是按什么规则抽的」不必回去翻代码的历史版本。
- 同一份产物再落一份进 `tests/fixtures/`（约 0.5 MB）并进数据契约，于是匹配测试在干净克隆里能跑，且抽取规则一旦被改动，契约校验会当场叫出来，而不是等下游数字变了才发现。
- 代价是多一次读写与一个必须先跑的前置阶段；匹配阶段因此要在路网产物缺失时 fail-fast 并提示先跑哪个阶段。
